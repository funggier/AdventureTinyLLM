# AIAdventureRPG / AdventureTinyLLM — เกณฑ์และวิธีคำนวณ Reward

**Release v0.2.0 · 2026-11-02 · สถานะ: ใช้งานใน Unity จริงและทดสอบ**

เอกสารนี้อธิบาย **กฎในซอร์สโค้ดจริง** ไม่ใช่แนวคิดในอนาคต จุดที่แก้ค่ารางวัลคือ
`Assets/AIAdventureRPG/Runtime/AdventureRewardPolicy.cs` (ใน Unity Example ที่แนบ Release) และการสร้างเหตุการณ์จริงอยู่ใน `AdventureStats.cs`, `AdventureAgent.cs`, `AdventureMonster.cs`, `AdventureCombatState.cs`, `AdventureTinyController.cs`.

## 1. หลักการตัดสิน: รางวัลจากผลจริง ไม่ใช่ความตั้งใจ

1. ตัวละคร **รับข้อมูลก่อนตัดสินใจ**: HP/MP, สถานะ Combat, ตำแหน่ง, สิ่งที่เห็น, ทิศและระยะของมอนสเตอร์ในวงตรวจจับ, การง้างโจมตี, หนามที่เห็นจริง และความพร้อมใช้สกิล (รวม 51 ค่า)
2. Tiny `POST /act` เลือกการกระทำจากโมเดลและคืน `action_id`; `TRAIN TINY` ใช้การสุ่มตามนโยบาย, `USE TRAINED` ใช้โมเดลโดยไม่อัปเดตน้ำหนัก
3. Unity ทำคำสั่ง **ในโลกเกม**: เดินเป็นระยะทางจำกัด, โจมตี, หลบ, เก็บสมุนไพร/MP, ตอบ NPC หรือใช้สกิล
4. เมื่อมีเหตุการณ์จริง Unity เก็บ **snapshot ก่อนเกิดเหตุการณ์** แล้วบันทึก `pre_hp`, `pre_mp`, `max_mp`, `hp_low_ratio`, `mp_low_ratio`, `HP/MP/Happiness/Boredom delta`, ชื่อเหตุการณ์และ `death=true` ถ้าตาย
5. `AdventureRewardPolicy.FromOutcome(delta, event)` คืนตัวเลข Reward โดยคำนวณจาก **ค่าที่เปลี่ยนจริง** และเหตุการณ์ที่ตรวจสอบได้
6. ในโหมด `TRAIN TINY` เท่านั้น Unity ส่ง `POST /experience` พร้อม `action_id`, `credit` และ Reward ให้โมเดลอัปเดตน้ำหนัก **ได้เพียงครั้งเดียวต่อ action ID**; ถ้าเงื่อนไขการส่งไม่ผ่าน จะ **ไม่อัปเดต** (ต่างจากส่ง `reward=0`)

**สำคัญ:** การสั่งให้วิ่งหนีอย่างเดียวไม่ถือว่าหลบสำเร็จ, การกดโจมตีเฉย ๆ ไม่ถือว่าโจมตีโดน, การเพิ่ม HP/MP ที่เต็มอยู่แล้วไม่ถือว่าได้ประโยชน์

## 2. สถานะก่อนเหตุการณ์ (State)

| สถานะ | เงื่อนไข |
|---|---|
| NORMAL | ไม่มีมอนสเตอร์ในระยะตรวจจับและช่วงรอเลิกต่อสู้สิ้นสุดแล้ว |
| COMBAT | มอนสเตอร์ที่มีชีวิตเข้ามาในรัศมีรอบตัว **9 หน่วย XZ** หรือเกิดเหตุการณ์โจมตี/ถูกโจมตี |
| เลิก COMBAT | หนีออกจากวงตรวจจับทุกตัวนาน **1.5 วินาที** (ค่าเริ่มต้น) |
| LOW HP | **HP ก่อนเหตุการณ์ต่ำกว่า 20/100** (ไม่รวมเท่ากับ 20) |
| LOW MP | **MP ก่อนเหตุการณ์ต่ำกว่า 20% ของ MaxMP** (ไม่รวมเท่ากับ 20%) |

`COMBAT`, `LOW HP`, `LOW MP` **เกิดพร้อมกันได้** เช่น `COMBAT / LOW HP / LOW MP`. ค่า Radius, Grace และ Threshold ปรับใน Unity Inspector ของ `AdventureCombatState` ได้ และ **สูตร Reward ใช้เกณฑ์ที่บันทึกก่อนเหตุการณ์จริง** ไม่อ้างอิงเกณฑ์เริ่มต้น 20% อย่างเดียว

Tiny รับสถานะผ่าน numerical features **43–50**; Ollama ได้ผ่านข้อความสถานะและ journal. หนามใช้เฉพาะสิ่งที่ตัวละคร **มองเห็น**, ไม่เปิดเผยข้อมูลที่ซ่อนอยู่

หมายเหตุ: ตารางนี้แสดงคะแนนหลัก ยังมีคะแนนเล็กน้อยจาก Happiness/Boredom และผลที่เกิดขึ้นจริง ค่า Reward ต่อเหตุการณ์จำกัด **[−2.00, +1.95]**

## 4. สูตรที่ใช้จริง

เริ่มต้น `score=0`; กรณี `death=true` คืนค่า **−2.00 ทันที** กรณี `ReadSign` คืนค่า **0** (แต่อาจไม่ส่งไปฝึกเลย) และ `AbilityRejected` / `AttackMiss` / `DodgeMonster` / `AvoidThorn` จะคืนค่าของเหตุการณ์นั้นโดยตรง

เหตุการณ์ทั่วไป:

```text
if ΔHP < 0:
    score += ΔHP × (LOW_HP_before ? 0.075 : 0.040)
elif ΔHP > 0:
    score += min(0.45, ΔHP × 0.012)
    score += LOW_HP_before ? (Herb ? 0.60 : 0.46) : 0.10
elif attempted_HP_pickup_or_heal:
    score -= 0.18

if ΔMP > 0:
    score += min(0.32, ΔMP × 0.009)
    score += LOW_MP_before ? 0.48 : 0.08
elif ΔMP < 0:
    score += ΔMP × 0.002
elif attempted_MP_pickup_or_reply:
    score -= 0.12

if normal_kill: score += 1.45
else if normal_hit: score += 0.25

if damaging_ability:
    if kills > 0: score += 1.45 + min(0.25, (kills-1) × 0.12)
    if hits > 0:  score += min(0.50, hits × 0.30)
    else:         score -= 0.22  # except Heal

score += ΔHappiness × 0.002 - ΔBoredom × 0.0002
reward = clamp(score, -2.00, +1.95)
```

**นิยาม:** `ΔHP`, `ΔMP`, `ΔHappiness`, `ΔBoredom` = *หลังเหตุการณ์ − ก่อนเหตุการณ์*; `LOW_HP_before` และ `LOW_MP_before` ใช้ snapshot ก่อนเกิดผล ไม่ใช้ค่า HP/MP ที่เหลือหลังโดนโจมตี

**การโจมตีซ้ำ/เวทหลายเป้าหมาย:** มีหนึ่ง Outcome `Ability hits=N kills=K` พร้อม MP ที่ใช้จริง ไม่ให้รางวัลจากการกดปุ่มอย่างเดียว

ตัวอย่างนี้ละส่วนความสุข/ความเบื่อออกเพื่ออ่านง่าย ยกเว้นระบุไว้

| กรณี | การคำนวณคะแนนหลัก | ผล |
|---|---|---:|
| โจมตีปกติโดน 1 ครั้ง | +0.25 | **+0.25** |
| โจมตีปกติฆ่ามอนสเตอร์ | +1.45 | **+1.45** |
| Special ตีโดน 1 ตัว ใช้ 12 MP | +0.30 − (12×0.002) | **+0.276** |
| Special ฆ่า 1 ตัว ใช้ 12 MP | +1.45 +0.30 −0.024 | **+1.726** |
| Arc Pulse ใช้ 20 MP และไม่โดน | −0.22 − (20×0.002) | **−0.260** |
| เสีย HP 10 เมื่อ HP ก่อนโดน = 65 | −10×0.04 | **−0.400** |
| เสีย HP 10 เมื่อ HP ก่อนโดน = 15 | −10×0.075 | **−0.750** |
| Herb ฟื้น HP 26 ขณะก่อนฟื้น HP = 15 | +(26×0.012) +0.60 | **+0.912** |
| Herb ฟื้น HP 26 ขณะก่อนฟื้น HP = 60 | +(26×0.012) +0.10 | **+0.412** |
| LoreStone เพิ่ม MP 18 ขณะก่อนเก็บ MP = 12 | +(18×0.009) +0.48 | **+0.642** |
| LoreStone เพิ่ม MP 18 ขณะก่อนเก็บ MP = 60 | +(18×0.009) +0.08 | **+0.242** |
| หลบการโจมตีที่ง้างแล้วพ้นระยะ | +0.35 | **+0.350** |
| หนีหนามหลังจากเห็นโดยไม่โดน | +0.28 | **+0.280** |
| ตายแม้ก่อนตายมีเหตุการณ์อื่น | death=true | **−2.000** |

ถ้าค่า HP ก่อนโดนเท่ากับ 20 พอดี จะ **ยังไม่ใช่ LOW HP** (ต้อง `<20`), และถ้าฟื้น HP/MP ตอนเต็ม ค่าเพิ่มจริงเป็น 0 จึงไม่ได้คะแนนฟื้น

## 6. การผูกเหตุการณ์กับหัวการตัดสินใจ (Action Attribution)

| `credit` | กรณีหลัก | สิ่งที่โมเดลปรับ |
|---|---|---|
| `move` | การเดินจริง, หนีหนามสำเร็จ, หลบการโจมตี, การเดินถูกบล็อก, โทษไม่เกิดความคืบหน้า | **ทั้งหัวทิศทางและหัวระยะเดิน** (กรณีมี action heads ครบ 5) |
| `interact` | โจมตีปกติ, โต้ตอบที่มีผล เช่นเก็บของ/กิน | หัวโต้ตอบ |
| `ability` | สกิลเกิดผล/สกิลถูกปฏิเสธ | หัวเลือกสกิล |
| `answer` | ตอบคำถาม NPC | หัวคำตอบ |

เงื่อนไขสำคัญ:
- ต้องอยู่ใน `TRAIN TINY` เท่านั้น และมี `action_id` จากคำสั่งที่ใช้จริง
- Unity รับผลภายในเวลาจำกัดที่สัมพันธ์กับคำสั่งล่าสุด (ปัจจุบันตรวจช่วงไม่เกิน **3 วินาทีเกม**); API มี TTL ของ `action_id` **20 วินาทีเวลาจริง**
- `action_id` ใช้ซ้ำไม่ได้; ถ้าผลลัพธ์เกินเวลา/ไม่ตรง/ได้รับการช่วยนำทางแบบ override ในกรณี movement จะ **ไม่ส่งน้ำหนักอัปเดต**
- ถ้ามีการช่วยหนีจากขอบแผนที่แบบบังคับ ก็ไม่ให้เครดิตด้านการเดินเหมือนเป็นทักษะที่ AI เรียนเอง
- คะแนนติดลบเล็กน้อยจาก `PassiveNoProgress` และ `PassiveZoneStay` ออกเมื่อไม่คืบหน้าจริง มี grace, limit และไม่ลงโทษเพียงเพราะอ่านป้าย

**ข้อจำกัดปัจจุบัน:** เป็นการฝึกแบบ one-step actor-critic ที่ผูกกับ action ID ล่าสุดที่ได้รับสิทธิ์ ไม่ใช่การแจกแจงความดีความชั่วข้ามหลายการกระทำ (multi-step credit assignment) การชน/การหลบที่เกิดหลังจากคำสั่งหลายชุดจึงอาจยังระบุสาเหตุไม่สมบูรณ์

## 7. +, −, 0 และไม่ให้ Reward

- **Reward บวก:** ผลดีจริง แต่การเพิ่มโอกาสทำซ้ำขึ้นกับ `Advantage = Reward − ValuePrediction`
- **Reward ลบ:** ผลเสียจริง แต่ยังเทียบกับความคาดหวังของโมเดล
- **Reward = 0 แล้วส่ง /experience:** ยังเกิดการคำนวณ loss และปรับน้ำหนักได้
- **ไม่ส่ง /experience:** ไม่มี optimizer update จากเหตุการณ์นั้นเลย เช่นอ่านป้าย, สั่งงานไม่สำเร็จและไม่มี action ID ที่ใช้ได้, อยู่ในโหมด `USE TRAINED`

สูตรฝั่ง Python โดยสรุป: `loss = −logπ(action)×(clamp(reward,−2,2)−V.detach()) + 0.5×(V−clamp(reward,−2,2))²`; สำหรับ Movement รวม `logπ(direction) + logπ(distance)`. ใช้ gradient clip และบันทึก checkpoint หลังรับ experience สำเร็จ

**ไม่มีรางวัลให้กับการมองเห็นอันตรายเพียงอย่างเดียว** ต้องหลบได้จริงแล้วจึงได้บวก; การมองเห็น/อ่านข้อมูลเป็น observation ไม่ใช่การกระทำที่สร้างแต้ม

## 8. การตรวจสอบและข้อควรระวัง

- Unity EditMode: **69/69** ผ่านในการตรวจล่าสุด (สถานะ/เงื่อนไขคะแนน/รีเซ็ต Ollama)
- Python pytest: ทดสอบการออกคำสั่ง โปรโตคอล action ID, action mask, optimizer, checkpoint; ต้องรันอีกครั้งก่อนสร้าง Release
- รอบตรวจ Play Mode ที่ผ่านมา: Tiny 51 features, ตัวอย่าง `USE TRAINED` ไม่มี API action failure, ได้ **66 online training updates** ใน checkpoint ที่เครื่องทดสอบ
- ผลการทดสอบ API สำเร็จหรือจำนวน updates **ยังไม่พิสูจน์** ว่านโยบาย AI เล่นเก่ง ควรประเมินหลาย seed/episode โดยเทียบกับ Random และ handcrafted baseline
- บางเหตุการณ์ยังต้องปรับ credit assignment โดยเฉพาะสถานการณ์ที่ AI สั่งหลายอย่างพร้อมกัน; อย่ามองคะแนนรางวัลว่าเป็นการพิสูจน์ความสามารถ
